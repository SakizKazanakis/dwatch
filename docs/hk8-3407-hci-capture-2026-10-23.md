# PHASE 03 — Verified HK8 PRO MAX 3407 Wearfit Pro BLE transfer
Date: 2026-10-23. Evidence: user-provided Android bugreport containing `FS/data/misc/bluetooth/logs/btsnoop_hci.log`. **The original bugreport / HCI trace is private and has NOT been committed.**

## Key result
A complete **OEM watchface** `wf_clock23` transfer was reconstructed from real HCI ACL/L2CAP/ATT traffic to the paired HK8 PRO MAX watch. SiFli transfer finishes with positive acknowledgements through END (9). The record does **not** prove that arbitrary `.so` binaries can be loaded or executed.

- Capture: 10,077 HCI records; about 19:22:19–19:33:53 Kyiv time.
- Transfer: 19:30:50.878–19:31:35.868 Kyiv time (44.990 seconds).
- ATT characteristic handle **0x0012** (the observed SiFli `00000000-0000-0200-6473-5f696c666973`): ATT Write Command **0x52** TX, Handle Value Notification **0x1B** RX.
- Separate Wearfit command channel: ATT handle **0x0016** TX, **0x0018** notifications RX.
- ATT MTU exchange: peripheral requests **1024** (`02 00 04`); Android responds **517** (`03 05 02`). Effective negotiated MTU **517**, but SiFli payload fragments in the captured transfer are capped at **244 bytes** per characteristic value. **Do not confuse observed packet length 247 with the negotiated MTU**.
- Outer SiFli envelope: category **4**, flags **0,1,2,3**, little-endian 16-bit message length in first frame. Multi-frame reconstruction shows no length discrepancies.
- Session start packet (complete outer frame, hex): `04 00 0b 00 00 00 07 00 00 00 02 a8 7c 01 00`. This is `CMD_START=0`, `type=0`, flag=2, **total 97,448 bytes**.
- Response start frame: `04 00 06 00 01 00 00 00 00 28`. Do not assign a meaning to trailing `00 28` without SDK confirmation.
- Commands and responses: **0→1** (1 pair), **2→3** (10 pairs), **4→5** (29 pairs), **6→7** (10 pairs), **8→9** (1 pair). All parsed result status fields are zero. No `CMD_INFO=13` in this particular session.
- Blocks: 4,096-byte file-data chunks, indices 1-based per file, 29 total.
- **10/10 file suffixes validated:** last 4 bytes equal CRC32/MPEG-2 of preceding bytes, encoded as little-endian u32. The user-captured file payloads already include CRC; `TYPE_FACE=0` must not add another CRC to such payloads.

Both `.so` files contain valid **ELF32 little-endian ARM (EM_ARM=40, ET_DYN, ARM EABI5, hard-float)** headers. `wf_clock23.so` exports `module_init`, `module_cleanup`, and `wf_clock23_register`. Its imports include `app_tileview_register_watchface`, `wf_view_init`, `lv_obj_align`, `lv_cont_create`, `rt_malloc`, `rt_free`, and `dlmodule_set_res_mng`; these establish a direct ABI/interface dependency on OEM watchface registration, LVGL, and RT-Thread/dlmodule symbol names. `wf_clock23_res.so` exports translation tables such as `lv_i18n_lang_pack`. `wf_clock23.dsc` refers to watchface module and resource names. Transfer and ACK success are confirmed, but execution and on-watch display cannot be proven solely from HCI.

## Matching Monolith status
The existing `SifliFilePush.java` uses UUID, category 4, type 0, command opcodes, 4096-byte blocks and 244-byte fragments that match these **observed** aspects of the OEM face transfer. Differences / outstanding risks:

1. The capture's `/ex/` directory is **verified for an OEM face (type 0)**, **NOT** for Monolith's custom background (type 3). The old dual-path upload strategy is not justified.
2. The Wearfit command channel in this OEM session has `AB`/`EA` messages; no `AD` custom-background transfer handshake is observed. No inference about separate custom background workflow follows.
3. Device-specific `boardType`, `DeviceLocalSupports.getType()`, response fields, backpressure and retransmission handling remain open for the custom-background path.
4. Never assume that the presence of official `*.so` modules guarantees unrestricted code loading or flashing of firmware.
5. **Keep Monolith uploader fail-closed** until the exact user-content workflow is captured and verified.

## Evidence handling
Only summarized UUIDs, opcode numbers, stock watchface resource names, sizes and non-sensitive protocol fixture bytes are committed. Do not commit raw HCI traces, bugreports, extracted OEM binaries, device MAC addresses or user content.
